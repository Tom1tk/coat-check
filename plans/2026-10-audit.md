# Coat Check — Kiosk Audit (2026-10-17)

Audit of `staging` @ `d7af640`. Baseline at time of audit: `npx tsc --noEmit`
clean, `npm test` 38/38 passing. Nothing in the code was changed by this audit.

The app is now a **wall kiosk in a porch, with nobody touching it**. Much of the
current design assumes a person at a desktop (hover spotlights, search box,
zoom bars, refresh button, theme toggle), and the refresh system was built for a
browser tab that keeps getting backgrounded. This audit is written for the kiosk.

## 2. Kiosk reliability: why it needed manual refreshes

These are the root causes of "previous attempts needed a manual refresh".

### K1 — Boot can stall forever on the map
`page.tsx` only shows the UI when `allReady = allWeatherLoaded && mapLoaded`.
`mapLoaded` only becomes true when MapLibre fires `load`. That depends on fetching
`basemaps.cartocdn.com/.../style.json` plus its sprites and glyphs. If any of
those fail during boot (Wi-Fi not up yet after a power cut, CARTO having a
problem), `load` never fires and nothing retries. The kiosk then sits on
"Loading weather data..." until someone presses F5.

**Fix:** Don't make the map a requirement for showing the UI. Render the weather
panel as soon as weather data exists (or as soon as cached data does, see K5).
Let the map fade in when it is ready. Add a map-level `error` listener and
rebuild the map with backoff if it hasn't loaded within about 20 s.

### K2 — The error state needs a human
`useWeather` sets `error`, and `page.tsx` then draws a full-screen modal over
everything with a **Retry** button. The last good data is still in state, but it
is hidden. Nothing retries automatically. The next attempt is the hourly refresh,
so one network blip blanks the kiosk for up to an hour.

**Fix:** After the first successful load, never block the screen. Keep showing
the last good data with a small "Last updated 14:05 · retrying" badge, and retry
with exponential backoff (30 s → 1 m → 2 m → … capped at 10 m).

### K3 — Refresh is scheduled by the clock, not by data age
`useAutoRefresh` is about 200 lines of heartbeat, `lastRefreshedHour` and
`localStorage` bookkeeping. It answers the question "has the hour changed?".
The kiosk actually needs to know "is any piece of data older than it should be?".
Because of this:
- The radar publishes a new frame **every 10 minutes**, but the kiosk only picks
  it up hourly. On average the radar you see is 30 minutes old.
- The heartbeat, `focus`, `pageshow` and BFCache handling exist for a tab that
  gets backgrounded. A full-screen kiosk tab is never hidden.
- `lastRefreshedDate` uses the *device* date while the forecast uses the
  *location* timezone. That doesn't matter in Cambridge but it is fragile.

**Fix (the simpler design):** Replace it with one scheduler. Each data source
declares a `maxAge`:

| Source | maxAge | Why |
|---|---|---|
| RainViewer frame index | 5 min | a new frame every 10 min |
| Open-Meteo `minutely_15` + `current` | 15 min | that is how often the model updates |
| Open-Meteo hourly/daily | 30 min | |
| Sun / theme / clock | 1 min tick | derived locally, no network |

A single 30 s `setInterval` (plus a `visibilitychange` check, which costs
nothing) runs `if (now - lastSuccess[source] > maxAge) fetch(source)`. With
backoff on failure, that covers everything the heartbeat did, in about 60 lines,
and needs no localStorage hour tracking. The countdown ("Auto Refresh in 0:42")
goes away. "Updated 2 min ago" replaces it.

### K4 — The refresh "blink"
`handleRefresh` sets `fade=true`, waits 1 s, refetches, waits 1 s and fades back
in. On a wall display, the whole screen blinks out every hour. **Fix:** swap the
data quietly. If anything, animate only the values that changed (number
crossfade). Keep full fades for user-initiated actions such as changing location.

### K5 — Stale data looks fresh, and cold boot is slow
- Add an "Updated HH:MM" indicator that changes to amber after 2× `maxAge` and
  red after 6×.
- Persist the last good Open-Meteo payload to `localStorage` (it's small) and
  draw it straight away on boot. Then a power cut followed by slow Wi-Fi shows
  slightly old weather instead of a loading screen.

### K6 — WebGL context loss
After a long uptime, display sleep or a GPU driver reset, the browser can drop
the WebGL context. MapLibre fires `webglcontextlost` and the canvas goes blank.
No handler exists. **Fix:** listen for it and remount `<Map>` by bumping a `key`.
This is the same remount used for the K1 boot-timeout recovery.

### K7 — Deploys vs a tab that never reloads
The kiosk runs whatever JS was loaded at boot, possibly for months.
`handleLocationUpdate` does a dynamic `import('suncalc')`. After a Vercel deploy,
the old chunk hash can 404 and throw `ChunkLoadError`. **Fixes:** (a) import
`suncalc` statically, since it is already in the bundle through `useSunCalc`;
(b) optionally, add a tiny `/api/version` that returns the build ID. If it
differs, show a "new version available" dot, and only reload automatically at a
quiet hour (e.g. 03:00) **if you opt in**. That is the only case where a reload
is justified. Data freshness never needs one.

### Kiosk host recommendations (outside the code)
- Launch Chromium with `--kiosk --noerrdialogs --disable-session-crashed-bubble
  --check-for-update-interval=31536000`. With these flags, crash bubbles and
  "Restore pages?" prompts don't cover the screen.
- Optionally request a Screen Wake Lock (`navigator.wakeLock`) so the display
  doesn't sleep. Or, the other way round, keep sleep and rely on the wake path.
  Both work with the K3 scheduler.

## 3. Rain map: what's possible with free sources

### Verified on 2026-10-17
I probed the live API (`api.rainviewer.com/public/weather-maps.json` and tile
URLs):
- `radar.past` has **13 frames** (2 h at 10 min intervals). `radar.nowcast` is
  **empty**.
- Colour schemes 1, 2 and 4 return **byte-identical tiles**. The `/2/` in
  `rainViewerTileUrl` is ignored. Everything is Universal Blue.
- `z=8` returns a grey **"Zoom Level Not Supported"** image. The existing
  `maxzoom: 7` overzoom guard is correct and must stay.
- `/512/` tiles at z7 work and are 512 × 512.

This matches RainViewer's [API transition FAQ](https://rainviewer.com/api/transition-faq.html)
(effective 2026-01-01: nowcast removed, single colour scheme, zoom capped at 7,
**100 requests/IP/minute**).

### R2 — Twice the detail for free: 512 px tiles
At z7, 256 px tiles cover about 1.2 km/px and look blocky when overzoomed to
z8–9. Requesting `/512/` and setting the source `tileSize: 512` makes MapLibre
use z7 data at the pixel density of z8. That is twice the linear resolution with
the same request count. Also consider smoothing option `0_0` (raw) instead of
`1_1`. Smoothing blurs the light showers that matter most for a coat decision.

### R3 — Animated loop of the last 2 h
The past 13 frames are free. A slow loop (frames 600 ms apart, a 2 s hold on the
latest frame) shows the direction of movement. That is the most useful thing a
radar can show you at a front door. **Rate-limit care:** at 1920 × 1080 with 512
tiles about 12 tiles cover each frame, so 13 frames is ~156 requests. Load the
frames gradually over about 2 minutes on boot, after which only the new frame
(12 tiles) is fetched every 10 minutes. Use one raster source per frame and
switch `raster-opacity` between them. Don't call `setTiles`, so cached tiles
stay hot.

### R4 — Replacing the lost nowcast: Open-Meteo `minutely_15`
I verified live: `minutely_15=precipitation` returns 15-minute steps for Cambridge.
For the UK, Open-Meteo blends in the Met Office UKV 2 km model. That gives a
**point nowcast** ("light rain from 08:30, dry by 09:15") without needing a
future radar layer. This is the most useful new data for the "do I wear the coat
**now**" question.

### R5 (experimental) — A forecast rain overlay from an Open-Meteo grid
Open-Meteo accepts many coordinates in one request. Querying a ~20 × 12 grid
around the location for hourly precipitation and drawing it as a smooth canvas
heatmap would give a **"next 6 hours" forecast map**, which RainViewer no longer
provides. Open-Meteo bills a multi-location request as several calls: 240 points ×
2 refreshes an hour is about 11.5k a day, above the 10k/day free limit. Hourly
refresh (about 5.8k/day) fits. Treat this as a spike, not a commitment.

### Sources ruled out
- **Met Office DataHub Map Images**: free (1000 images/day), but the
  precipitation layer comes from the **global model**, which is coarse, and
  [radar is not free](https://www.metoffice.gov.uk/services/data/datapoint/datapoint-retirement-faqs)
  since DataPoint was retired. Not better than RainViewer.
- **OpenWeatherMap `precipitation_new`**: also model output and coarse. It's
  fine as the existing fallback, but don't promote it.
- **LibreWXR** ([GitHub](https://github.com/JoshuaKimsey/LibreWXR)): a
  self-hostable radar tile server that mimics the RainViewer API. Worth watching
  if RainViewer tightens further, but it adds hosting. Not recommended now.

## 4. Forecast data and coat logic

### D1 — Weather codes
`codeToCondition` maps only 0, 1–3, 45/48, and 51–65. UK showers (80–82) are
probably the most common rain code here, and they become `"Other"`, which
`getCoatAdvice` doesn't treat as rain (it only checks `rain > 0`). Freezing
drizzle and rain (56/57/66/67), snow (71–77, 85/86) and thunder (95–99) are
missing too. **Fix:** a complete WMO code table → `{ label, icon, wet: boolean }`.

### D2 — The commute is a window, not two hours
Today: the 08:00 and 17:00 hourly values only. Better:
- **Out window** (e.g. 07:30–09:00) and **back window** (e.g. 17:00–18:30),
  taking the max `precipitation_probability`, the sum of `precipitation`, the
  minimum `apparent_temperature` and the max `wind_gusts_10m` across each window.
- Weekends: no fixed window. Use "the next 12 hours of daylight".
- A graded verdict replaces the three strings:
  **Coat on now** / **Coat in bag** (dry now, wet later) / **Light layer** /
  **No coat**, and optionally an umbrella flag (rain, low wind).
  "Coat in bag" answers your weekday scenario directly.

### D3 — Thresholds
Use `precipitation ≥ 0.2 mm` **or** `probability ≥ 50%` as "wet". Use
`apparent_temperature` (which includes wind chill) instead of
`temperature_2m < 10`. Put thresholds and windows in one `config.ts` (the
earlier audit's direction option B).

### D4 — One request, more fields
Ask for everything in one call:
`current=temperature_2m,apparent_temperature,precipitation,weather_code,wind_speed_10m,wind_gusts_10m`
`&minutely_15=precipitation&forecast_minutely_15=12`
`&hourly=temperature_2m,apparent_temperature,precipitation,precipitation_probability,weather_code,wind_speed_10m,wind_gusts_10m`
`&daily=weather_code,temperature_2m_max,temperature_2m_min,precipitation_sum,precipitation_probability_max,wind_speed_10m_max,wind_gusts_10m_max,sunrise,sunset,uv_index_max`
`&forecast_days=8&timezone=auto&wind_speed_unit=mph`.
Also: `weathercode` is the legacy alias, so use `weather_code`. Replace the
`any`-typed response with a validated shape (zod or a hand-written guard like
`latestRadarFrame`). `daily.sunrise/sunset` also makes the client-side `suncalc`
dependency unnecessary.

## 5. UI, code quality and tooling

- **U1 — Controls on a kiosk.** Search, zoom bars, theme toggle, the refresh
  button and the countdown use about 15% of the screen and get no input. Move
  them to a hidden settings sheet (long-press the location name, or open
  `?settings`), and let URL params pin the config (`?lat=…&lon=…&name=Cambridge`)
  so the kiosk survives cleared storage.
- **U2 — SpotlightCard / SpotlightText.** Their mouse-tracking gradient never
  appears without a pointer. Remove them from the kiosk build.
- **U3 — Map centring.** The left-panel layout needs the location dot centred in
  the *remaining* area. MapLibre supports this natively: `map.setPadding({ left:
  panelWidthPx })`. Then `flyTo` / `center` centre within the padded area with no
  coordinate maths. Recompute it on `resize`.
- **U4 — Legibility at 2–3 m.** Helvetica at `text-xl` is too small for a glance
  from the coat rack. The verdict needs to be about 6–8 vw, with tabular numerals.
- **U5 — Burn-in.** For a static layout on an always-on panel, add a 1–2 px
  pixel shift every few minutes and dim it at night (the theme already follows
  sunset).
- **U6 — Weather moods (suggested by you, mockup board F).** The whole theme
  takes the colour of the *next 3 hours*, so the screen reads before any text
  does:
  - Six moods: clear & mild, overcast, rain, cold/frost, storm/gale, and clear
    night.
  - Hue comes from the weather code and the feels-like temperature (D1);
    darkness comes from sunrise/sunset. This replaces the current light/dark
    toggle in `useAutoTheme`.
  - Put it in a pure `getMood(forecast, now)` in `utils/` that returns a palette
    key, and apply it as `data-mood` on `<html>`. Define each palette as CSS
    custom properties in `globals.css`, not Tailwind class names, which keeps to
    the dynamic-class rule.
  - Basemap: use CARTO Positron/Dark Matter with a 10–14% colour overlay. Leave
    the radar untinted so the rain colours keep their meaning.
  - Guardrails:
    - Hysteresis: a new mood must hold for two updates.
    - Use a 60 s crossfade.
    - Check WCAG AA contrast for each palette (add a unit test).
    - Orange always means "coat", whatever the mood.
  - Night moods also help with U5 (burn-in).
- **Q1 — Leaked timers.** `handleRefresh`, `handleDayToggle`,
  `handleLocationUpdate` and `handleThemeToggle` nest `setTimeout`s that are never
  cleared. Most of them go away with K4 / U1.
- **Q2 — Shared fade props.** `fade` / `pageVisible` / `FADE_DURATION` are
  threaded through every component. A single wrapper (`<Reveal>`) or a CSS class
  on the root removes the prop drilling.
- **Q3 — `useSunCalc` only recomputes on wake/refresh**, so the theme can flip
  up to an hour after sunset. This goes away with the 1-minute clock tick in K3.
- **T1 — Dependencies.** `eslint-config-next` is still blocked on the FlatCompat
  migration (plan 009). MapLibre 6 and lucide 1.x are major bumps, so do them
  as separate, tested changes.
- **T2 — CI** runs on `main` and on PRs but not on pushes to `staging`, which is
  where work lands.

## 6. New feature candidates

Ranked by how directly they answer "do I need a coat, and when?":

1. **Next-2-hours rain strip** (from `minutely_15`). "Dry for 40 min, then light
   rain." Answers "coat on now, or in the bag?".
2. **Out / Back verdicts** (D2). Two big verdicts plus the reason, e.g. "Back
   17:30 · 70% showers · feels 6°".
3. **7-day forecast, Apple-style.** Per day: icon, condition, low–high bar on a
   shared weekly scale, precipitation % and mm, wind/gust, weekend rows tinted.
   Each day gets a small coat badge. That covers the "away Saturday to Sunday"
   case with no input.
4. **Animated radar loop** with a timestamp (R3).
5. **Next 48 h strip** for trips: temperature line plus rain bars across two days.
6. **Met Office warnings** banner (free regional RSS feed). It only appears when
   a warning is active.
7. **Pollen and air quality** (Open-Meteo Air Quality API, free, covers Europe):
   a small chip when levels are high.
8. **Sunrise and sunset, UV, and a large clock.** Free from the daily block.
   **Weather moods** (U6) belong near the top of this list for at-a-glance
   value. They're cheap once D1 and D4 are in.
9. **Optional calendar awareness** (an ICS URL) to set the "back" time from your
   calendar. Later, and only if wanted.

1. **Reliability first** (K1, K2, K3, K4, K5, K6, K7): one plan, "kiosk-grade
   data scheduler". It's mostly a deletion. Done means the kiosk survives a
   pulled network cable for an hour and recovers with no input.
2. **Data model** (D1–D4, the config file) with tests. It's pure functions, so
   it's easy to cover.
3. **Radar upgrade** (R2, R3) and the R4 nowcast data.
4. **Layout redesign**, using whichever mockup variant you pick (U1–U6, and
   features 1–5).
5. Extras (warnings, pollen, R5 spike, dependency majors).

Each step can become a numbered plan in `plans/` in the existing format once you
have chosen a design direction.
