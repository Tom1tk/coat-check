## Why this matters

The repo has zero tests, no test script, and no CI. The core product logic —
"do I need a coat" — is pure and trivially testable, yet nothing verifies it,
and the riskiest pending fix (plan 005, timezone handling in date
derivation) cannot land safely without characterization tests first. After
this plan: `npm test` runs a real suite covering the coat rules, weather-code
mapping, and the derivation functions, and GitHub Actions blocks regressions
on every push.

## Steps

### Step 1: Install and wire Vitest

1. `npm install --save-dev vitest`
2. Add scripts to `package.json`: `"test": "vitest run"`, `"test:watch": "vitest"`.
3. Create `vitest.config.ts`:
   ```ts
   import { defineConfig } from 'vitest/config';

   export default defineConfig({
       test: {
           include: ['src/**/*.test.ts'],
           environment: 'node',
       },
   });
   ```

**Verify**: `npm test` → runs, reports "no test files found" (or 0 tests) with
a non-crashing exit. `npx tsc --noEmit` → exit 0.

### Step 2: Test the pure utils

Create `src/app/utils/coatAdvice.test.ts` covering at minimum:
- rain > 0 in any period → `'Bring a coat'`
- temp < 10 (including exactly 0 and 9.9) → `'Bring a coat'`
- temp exactly 10, Cloudy → `'Coat recommended but not necessary'`
- temp exactly 15, Cloudy → `'Coat recommended but not necessary'`
- temp 15.1, Cloudy → `'No need to bring a coat'`
- temp 12, Clear, no rain → `'No need to bring a coat'`
- two periods where only the second triggers each rule
- empty period array → `'No need to bring a coat'`

Create `src/app/utils/weatherUtils.test.ts`:
- code 0 → 'Clear'; 1/2/3 → 'Cloudy'; 45/48 → 'Fog'; 51/61/65 → 'Rain';
  71 (snow) → 'Other'; 95 (thunderstorm) → 'Other'.

Test style: plain `import { describe, it, expect } from 'vitest'`.

**Verify**: `npm test` → all pass.

### Step 3: Characterize the derivation functions

1. In `src/app/hooks/useWeather.ts`, add `export` to `deriveCurrentHourWeather`
   and `deriveDayWeather` (no other change).
2. Create `src/app/hooks/deriveWeather.test.ts` with a fixture builder that
   produces a realistic Open-Meteo response (7 days of hourly arrays, local
   timestamps, chosen `utc_offset_seconds`).
3. Use `vi.useFakeTimers()` + `vi.setSystemTime(...)` to pin the browser clock.
4. Cases:
   - **Happy path**: browser in UTC (`vi.setSystemTime(new Date('2026-07-05T10:30:00Z'))`),
     fixture offset 0, timestamps starting `2026-07-05T00:00` →
     `deriveCurrentHourWeather` picks the `10:00` entry;
     `deriveDayWeather(data, 0)` picks `08:00`/`17:00` of 2026-07-05;
     `(data, 1)` picks 2026-07-06.
   - **Characterization (today's buggy behavior — mark each with a comment
     `// BUG documented, fixed by plan 005`)**:
     - Current hour missing from `times` → returns the `Math.floor(times.length / 2)` entry.
     - `deriveDayWeather` date missing from `times` → fields are `undefined`
       (assert `toBeUndefined()`).
     - Browser at `2026-07-06T01:00:00Z` with fixture in UTC−7 (offset
       −25200, local date still 2026-07-05): `deriveDayWeather(data, 0)`
       uses the **UTC** date 2026-07-06 — assert it returns the 07-06 values,
       i.e. the wrong day. This is the exact regression test 005 will invert.

**Verify**: `npm test` → all pass. `npx tsc --noEmit` → exit 0.

### Step 4: Add GitHub Actions CI

Create `.github/workflows/ci.yml`:

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npx eslint src
      - run: npx tsc --noEmit
      - run: npm test
      - run: npm run build
```

Note: `npm run build` succeeds without `NEXT_PUBLIC_OWM_API_KEY`; the key is
only read at runtime in the client. Do not add secrets to the workflow.

**Verify**: `npx tsc --noEmit`, `npx eslint src`, `npm test`, `npm run build`
all exit 0 locally — the same sequence CI runs.
